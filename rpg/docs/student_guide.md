# Student Guide: Build Your Own Battle Game

This RPG is meant to grow with you. You can begin in one short file and later
work on game AI, procedural graphics, mathematics, simulations, or the engine
itself without throwing away your earlier work.

## Level 0 — Start in the workshop

Open:

```text
student_game/workshop.py
```

Do **not** begin by trying to understand the whole repository.

The workshop contains four real pieces of the game:

- `power_strike_logic` — an `if` statement;
- `chain_lightning_logic` — a `for` loop over targets;
- `workshop_hero` — a character assembled from reusable objects;
- `practice_enemy_strategy` — a small decision-making algorithm.

Play only that battle:

```bash
python main.py --encounter workshop
```

A good first edit is changing `0.50` in:

```python
if ctx.user.hp_ratio < 0.50:
```

Predict what the change will do before running it.

## Level 1 — Use the move laboratory

A playable battle gives useful feedback, but it contains many things at once.
The lab lets you isolate one function.

```bash
python lab.py move workshop_power_strike --user-hp 50 --seed 3
python lab.py move workshop_power_strike --user-hp 10 --seed 3
```

The random seed is the same, so the health value is the important change.
Compare:

- the value of `ctx.user.hp_ratio`;
- which branch executes;
- the `Damage(...)` command returned by the function;
- the final damage event generated by the real engine.

List all moves with custom Python functions:

```bash
python lab.py list --scripted
```

## Level 2 — Values, references, and composition

Try changing:

- `hp`, `attack`, `magic`, or `speed` on `workshop_hero`;
- `sprite=art.knight_dawn` to another sprite;
- one item in `moves=[...]`;
- the music on `workshop_battle`.

These are ordinary Python variables referring to objects. A character holds
actual `Move` objects; a battle holds actual `Team` objects.

Then explore the larger libraries in `student_game/characters.py`, `moves.py`,
`art.py`, `effects.py`, and `audio.py`.

## Level 3 — Write a conditional move

The workshop starts with:

```python
def power_strike_logic(ctx):
    if ctx.user.hp_ratio < 0.50:
        return damage(18)
    return damage(8)
```

Useful read-only facts include:

- `ctx.user.hp`, `max_hp`, and `hp_ratio`;
- `ctx.user.attack`, `defense`, `magic`, and `speed`;
- `ctx.user.statuses`;
- `ctx.target` for the first target;
- `ctx.targets` for every target;
- `ctx.round_number`.

Useful commands include:

```python
damage(12)
heal(10, target="user")
add_status("burn", turns=2)
change_stat("speed", 2, target="user")
```

`python main.py --check` now smoke-tests custom move functions with several
deterministic contexts. A bad return value becomes a short validation problem
that includes the source location of the function.

## Level 4 — Use a loop to treat targets differently

`chain_lightning_logic` demonstrates something the engine specifically supports
for programming exercises:

```python
def chain_lightning_logic(ctx):
    commands = []
    for target in ctx.targets:
        if "burn" in target.statuses:
            commands.append(damage(14, magical=True, target=target))
        else:
            commands.append(damage(8, magical=True, target=target))
    return commands
```

`target` is a read-only `BattlerView`. Passing it back into `damage(...,
target=target)` safely tells the engine which battler that command belongs to.
The student function never receives mutable battle state.

Run a controlled two-target experiment:

```bash
python lab.py move workshop_chain_lightning \
    --target spirit \
    --target guardian \
    --target-status 2:burn \
    --seed 3
```

Ideas:

- make damage depend on each target's HP;
- heal allies below half health;
- apply a status only to targets that do not already have it;
- build a list of commands in two separate loops and compare the result.

## Level 5 — Program enemy strategy

A team may provide a normal Python strategy function:

```python
def practice_enemy_strategy(turn):
    if turn.user.hp_ratio < 0.30:
        return turn.defend()

    target = min(turn.enemies, key=lambda enemy: enemy.hp_ratio)
    return turn.use(moves.arc_bolt, target=target)
```

The engine passes in a read-only `TurnContext`. It exposes:

- `turn.user`;
- `turn.allies`;
- `turn.enemies`;
- `turn.round_number`;
- `turn.use(move, target=...)`;
- `turn.defend()`.

A strategy cannot silently use a move the character does not know, and its
chosen target must be legal for that move.

Challenges:

- attack the enemy with the lowest HP;
- defend every third round;
- use one move above half health and another below half health;
- design a boss with two or three recognizable phases.

Use:

```bash
python main.py --encounter workshop --teach
```

to watch custom strategies and custom move functions execute while playing.

## Level 6 — Make a new character and battle

Characters are compositions of things you already understand:

```python
comet_witch = Character(
    "Comet Witch",
    role="mage",
    hp=45,
    attack=4,
    defense=5,
    magic=13,
    speed=8,
    sprite=art.moon_mage,
    moves=[moves.ember, moves.mist_veil, moves.strike],
)
```

You can prototype it in `workshop.py`. You only need to move it into a larger
module after the workshop itself becomes inconvenient.

That transition is a useful reason to learn modules: split a program because it
has grown, not because a tutorial told you that every project must start with
many files.

## Level 7 — Draw with geometry

`student_game/art.py` builds sprites from primitives:

```python
my_sprite = Sprite("My Sprite", my_palette)
my_sprite.circle((0, 0), 40, fill="body")
my_sprite.polygon([(-25, -20), (0, -60), (25, -20)], fill="accent")
my_sprite.face(-8)
```

Preview one character instead of replaying a battle:

```bash
python render_character.py knight
```

Coordinates, symmetry, loops, and functions can all become visible drawing
problems.

## Level 8 — Program mathematical spell paths

`student_game/effects.py` contains both preset paths and ordinary Python
functions. For example:

```python
def classroom_wave(x):
    envelope = 1.0 - 0.45 * x
    return math.sin(x * math.tau * 3) * 30 * envelope
```

Preview effects with:

```bash
python render_effect.py sine_wave
python render_effect.py classroom_wave
```

Try piecewise functions, damping, harmonics, parabolas, or noisy waves.

## Level 9 — Turn balance into an experiment

The headless simulator plays both sides automatically through the real battle
controller and rules:

```bash
python simulate.py --encounter workshop --runs 100 --seed 0
```

It reports wins, average rounds, and common moves. Because run `N` always uses
seed `seed + N`, you can change one rule and rerun exactly the same seed range.

Questions you can investigate:

- Does changing power from 8 to 10 materially change the win rate?
- Does a new AI branch shorten battles?
- Is a boss more difficult because it has more HP or because its strategy is
  better?
- How many simulations do you need before an average becomes stable?

This is a bridge from programming into experimental design and basic statistics.

## Level 10 — Explore the engine

When you want to know *why* something happens, follow it downward:

```text
student_game/workshop.py
  -> rpg_battle.api.Move / Team
  -> core.models.MoveSpec / TeamSpec
  -> core.scripting read-only contexts and commands
  -> core.rules / core.ai
  -> battle/battle_scene.py
```

At this point the engine is not mysterious infrastructure. It is the
implementation of concepts you have already used from the outside.

## Debugging

Start with:

```bash
python main.py --check
```

For readable custom-code execution traces:

```bash
python main.py --encounter workshop --teach
```

For lower-level engine logging:

```bash
RPG_BATTLE_LOG_LEVEL=DEBUG python main.py
```

Syntax errors and `NameError`s are normal Python errors and still show ordinary
tracebacks. Cross-object content mistakes and malformed custom move results are
validated before pygame starts.
